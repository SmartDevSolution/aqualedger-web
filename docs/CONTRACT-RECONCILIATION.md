## Compatible surface consumed

The artifact contains exactly the M1 routes `POST /analyses`, `GET /analyses/{analysis_id}`, `GET /analyses/{analysis_id}/result`, and `GET /sources`. The web client generates its types from that file. It sends an idempotency key for each explicit submit attempt, treats `IDEMPOTENCY_CONFLICT` as an explicit error, and sends only the AOI, ISO start/end dates, and presentation locale. Locale and browser timezone never trigger a submission. The UI has no history, zones, time-series/trend, or priority presentation; those fields are absent from the consumed result schema. The re-pinned artifact adds several typed fields the client now accepts and validates — a required `baseline` object, a typed `ArtifactReference` (replacing an arbitrary object), nullable `ndvi_min`/`max`/`mean`/`median`/`p05`/`p95`, and per-date `data_present_overlap_count`, `masked_yielded_coverage_count`, `discarded_candidates`, and `failures` on `SceneSelection` — but this PR does not add new UI surface for them beyond what W1 required; they are typed and validated, not newly displayed.

## Differences requiring backend/central follow-up

1. **Failed-run evidence status:** freeze B4 requires `evidence_status` to be absent when `execution_status` is `FAILED`. At the previous pin, the generated status schema required it unconditionally, contradicting the freeze outright. The re-pinned artifact changes `AnalysisStatusResponse.evidence_status` to optional and nullable, which at least stops asserting the opposite of the freeze rule in the schema; the web client still accepts a `FAILED` status only when the JSON field is absent (not merely `null`) and reports a contradictory response as contract-invalid. Whether the pinned backend route actually omits the field on every `FAILED` response was not independently re-verified in this PR (no live backend run was performed here) and stays NOT RUN.
2. **Authorization declaration and delivery — RESOLVED under the recorded access model.** This was BLOCKED pending an approved access model; it is now implemented under the Council DP-2 verdict recorded on `AmeenBinBisher/aqualedger#8` ("Council verdict RECORDED — DP-2 parameters + access model"): a server-only `AQUALEDGER_OPERATOR_JWT` and `AQUALEDGER_API_BASE_URL`, read only by `src/lib/api/server-config.ts` (marked `server-only`) and used by the same-origin route handlers under `src/app/api/**`. The Bearer is added only on `POST /analyses`, `GET /analyses/{id}` and `GET /analyses/{id}/result`; `GET /sources` is relayed without it; any inbound `Authorization` from the browser is dropped, never forwarded. This is not an end-user login or a new application secret — the backend still authorizes every request against the single pinned operator principal (backend PR #3's fail-closed `sub` pin). The artifact still marks `Authorization` optional on these operations at the schema level, which remains a minor documentation-only mismatch since the backend enforces it regardless of what the schema declares.
3. **Frozen error envelope and responses — schema gap closed, backend behavior not independently re-verified.** At the previous pin, the artifact did not describe `{error: {code, params, request_id}}` or the frozen error responses at all. The re-pinned artifact now declares `ErrorEnvelope`/`ErrorDetail` schemas and 400/401/403/404/409/500/503 responses on every M1 operation, and `GET /analyses/{id}/result`'s `200` response is now documented as `anyOf: [AnalysisResult, ErrorEnvelope]` with `NOT_READY` still a `200` (freeze B4). The client's runtime envelope detection (`readErrorEnvelope` in `src/lib/api/client.ts`) already handled this shape at runtime before the re-pin and is unchanged; the schema now agreeing with that runtime handling is a documentation improvement, not new behavior. The relay's own passthrough of this exact shape, including a `200` `NOT_READY` and a signed `preview_url`, is exercised in `tests/e2e/relay.spec.ts` against the labelled-double backend fixture — that is a real, locally-run assertion, not a claim of live-backend acceptance.
4. **Baseline result field — schema gap closed, no new UI added.** Freeze B4 requires a baseline identity in the result. At the previous pin, `AnalysisResult` had pipeline/method versions and provenance but no explicit `baseline` field. The re-pinned artifact adds a required `Baseline` schema (`contract_version`, `collection`, `offset_rule`, `mask_policy_version`, `grid_crs`, `grid_resolution_m`, `pipeline_version`) to `AnalysisResult`. The generated type and the client's runtime validator (`isBaseline` in `src/lib/api/client.ts`) now require and accept it; this PR's authorized scope (the backend re-pin and the access-model relay) did not include adding a result-panel display for it, so the field is validated but not yet rendered.
5. **Acquisition tie-break metric:** freeze B2 rule 5 defines a mosaic cloud metric as the maximum `eo:cloud_cover` across selected tiles of a date. Whether the re-pinned pipeline still computes a mean rather than a max was not independently re-verified in this PR (no backend source/behavior review was performed here beyond the OpenAPI artifact diff); this item is carried forward unchanged pending that verification, not asserted as fixed or as still-broken.
6. **No-eligible-date reason:** freeze B2 rule 6 requires `NO_ELIGIBLE_ACQUISITION` when every evaluated date is rejected. Whether the re-pinned pipeline still returns `NO_DATE_MEETS_MIN_VALID_COVERAGE`/`NO_SCENES_FOUND` instead was not independently re-verified in this PR; this item is carried forward unchanged for the same reason as item 5.
7. **Georeferenced map preview:** freeze B9 requires a backend-rendered, georeferenced preview with recorded bounds/CRS and a fixed colormap. The re-pinned artifact's `ArtifactReference` schema now declares `bounds`, `crs`, `resolution_m`, and `ready` fields (typed, where the previous pin had an arbitrary object), which is consistent with the freeze's shape but was not independently re-verified against a live worker run in this PR — whether the pinned backend actually populates non-null `bounds`/`crs` for a real run stays NOT RUN. The web client validates and would accept these fields if present; the map overlay itself remains explicitly NOT RUN, and no raster is fabricated or decoded in the browser.

The web PR must link these exact differences for the backend owner and report the corresponding UI paths as NOT RUN/BLOCKED. Any correction to the generated contract or ratified freeze belongs in the owning repository and requires its review; the checked-in artifact is not edited here.
